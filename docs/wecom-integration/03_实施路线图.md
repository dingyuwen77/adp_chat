## 0. 目标、限制与完成定义

用户可观察结果：企业员工在**企业微信自建应用原生消息会话**发文字，网关通过可信回调确认员工身份，保存消息并快速 ACK，后台交给 ADP 单轮 `chat()`，最后把回答主动推送给该员工。员工切出应用/重新进入不应取消服务端请求；多员工可并行、同员工有序，跨重启能区分哪些动作可恢复、哪些已进入未知结果，不让会议 MCP 被盲目重复执行。

**已经决定**：单企业单应用、可信企业微信 UserID 作为 ADP UserId/VisitorId、稳定派生 ConversationId、同员工新消息忙碌即拒绝而不排队、不同员工不设置人为 ADP 业务并发限额、ADP 零自动重试与限额错误解释、UNKNOWN 通知后释放本地占用、通知状态与 ADP 会话占用解耦、不判断追问是否完成或员工已读、单实例 JSON 快照与 JSONL 日志、PyCharm + Docker Compose、首期不引入数据库/Redis、未来 Cosmos DB 仅评估用于**日志**。**当前阶段 A～E 只需要本机/可信内网 HTTP 与测试协议夹具**，不要求公网域名、HTTPS 证书或真实企微应用 Secret。

**尚未实现**：企业微信回调和主动发送、消息调度与清理、网关 JSONL、Cosmos DB、H5 页面。**不提前扩展**：多租户、群聊、附件、OAuth 前端、MCP 写操作身份传递与生产回调之外的内部公共 REST API。当前 `/api/v1/chat` 仍是无鉴权、固定身份的单用户接口，不能被当作企微回调路由，更不能暴露到公网。

工程上的协议/鉴权属于高风险边界；正式实现阶段必须按项目与当前 canonical Agent_Skills 的 Coding/Testing/Docs/Review/Git 门禁进行，不能仅因阶段拆分就降低验证要求。本文是长期 roadmap，不作为第二份自动生成 Change 文档。

## 1. 核心架构选择

| 设计选择 | 推荐结论 | 实际原因 |
| --- | --- | --- |
| 一条消息一个 JSON vs 追加 JSONL | **JSON 快照做业务状态、JSONL 做日志** | 状态要频繁更新/按 MsgId 定位；追加事件需要回放与压缩。迁移数据库依赖状态接口，不依赖 JSONL |
| 企业微信用户退出应用 | **服务器继续处理 + 企微应用主动推送** | 不是客户端同步 SSE，员工离开时不会取消服务器任务；真正展示/历史依赖企微客户端，要实测 |
| 日志与状态是否共用存储 | **分离** | 诊断日志不能替代可恢复任务状态；Cosmos 故障不能引起 ADP 副作用重复执行 |
| 同用户连续新消息 | **忙碌即拒绝，不自动排队** | 首次接收时原子占用；相同 MsgId 先去重，不重复生成通知 |
| 跨用户并发 | **不设人为 ADP 业务配额** | 尽可能立即异步转发；ADP 决定配额拒绝，网关仅做物理资源保护 |
| ADP 结果未知 | **保存 UNKNOWN、释放本地会话并通知** | 不自动重投；接受旧云端轮次可能仍执行、上下文可能重叠 |
| 企业微信消息发送 | **独立记录 API 结果，不跟踪已读** | API 接受即完成网关发送，失败不重新调用 ADP |
| HTTP 与 HTTPS 是否两套程序 | **同一 FastAPI GET/POST 回调路径** | 本地 HTTP 可验证业务协议；以后若满足真实企微可达性要求，可原路径接入 HTTP 或经 TLS 反向代理接入 HTTPS；仅传输层不同 |

### 阶段 A：源码/协议基线与纯身份函数（第一批）

**依赖**：当前 main、已发布且允许测试的 ADP 应用 AppKey；CorpID、AgentId、两名 UserID 可先使用虚构测试值，不需要真实企微 Secret/回调地址。

实施：
- 保留 [main.py](../../main.py) CLI 和 [src/adp/client.py](../../src/adp/client.py) 的单轮行为。
- 在纯身份函数中使用明确的 CorpID、AgentId、WeCom UserID 和**固定配置的 ADP 逻辑应用名**确定性计算 64 个十六进制字符的 ConversationId；UserId=VisitorId=WeCom UserID，跨进程不存 UserID→ConversationId。真实回调身份只有在阶段 F 完成企业微信验签后才可信，本阶段输入仅为测试身份。
- 核实当前 ADP V2 格式及上下文配置；单元测试和真实跨进程两轮测试分别证明 ID 相同及平台仍能回忆先前信息。

验收保持 A1～A5 原有标识和语义；为现有 Change 机器校验提供 AC1～AC5 一对一锚点别名：

- <a id="AC1"></a> **A1** 同一模拟员工同一逻辑应用跨重启 ID 一致。
- <a id="AC2"></a> **A2** 不同员工/应用不相同。
- <a id="AC3"></a> **A3** 当前 CLI 与 `/api/v1/chat` 输入输出及 V2 兼容回归不退化。
- <a id="AC4"></a> **A4** 明确提示“固定 ID 不等于永久记忆”。
- <a id="AC5"></a> **A5** 真实 ADP 测试账号跨进程两轮上下文续接有直接证据（环境不可用时如实标为未验证）。

### 阶段 B：企业微信回调、原子接收决策与可靠 ACK

**依赖**：阶段 A、本机 HTTP、模拟 CorpID/AgentId、测试 Token/EncodingAESKey；不依赖公网、真实 Secret 或员工端。

实施：
- 在正式 FastAPI 增加 `GET/POST /wecom/callback`；验证企业微信 URL 校验、POST 签名、AES XML、企业/应用/员工身份，限制恶意 XML 和请求大小；非文字消息/事件暂不调用 ADP。不得暴露未鉴权 `/api/v1/chat`。
- 先按 `(CorpID, AgentId, MsgId)` 去重，再在单实例受保护临界区对**新消息**原子完成用户占用检查、获准 `RECEIVED` 或 `REJECTED_USER_BUSY` 决策、JSON 快照和一次待通知意图可靠提交；状态保存成功才 HTTP 200 空 ACK。
- 同用户忙碌消息不排队、不调用 ADP，等待本轮结束后必须由用户主动重新发消息。重复 MsgId ACK 但不新建执行、不新生成 BUSY 提示。
- 阶段 B 提供最低可靠的 `put_if_absent/get` 与接收判定，阶段 C 继续扩展同一个存储 Owner，不引入第二套状态源。

验收：B1 GET/POST 正式协议夹具；B2 错误签名/加密/企业应用身份拒绝；B3 同用户并发两条新消息仅一条获准，另一条保存 BUSY 提示；B4 重复 MsgId 只处理一次；B5 状态落盘失败不能 ACK；B6 非文字/事件不投 ADP。

### 阶段 C：异步 ADP 转发、错误分类和持久化恢复

**依赖**：阶段 B；正式状态与失败语义 Owner 为 [docs/wecom-integration/01_网关架构设计.md](01_网关架构设计.md)。

实施：
- 在现有消息快照上扩展 `update/list_unfinished/purge`、版本检查、目录独占、可靠原子替换、启动重建占用及安全恢复；不另造任务数据库/Redis。
- 新网关出站使用真正的异步 HTTPS/SSE，独立用户并发，**不加模型配额业务信号量/限额队列/自动重试**。保留必要的连接池、磁盘、内存等物理资源保护。原 `main.py`、CLI、单用户 `/api/v1/chat` 与互斥行为保持兼容。
- 每条获准消息以可信 WeCom UserID 形成独立 UserId/VisitorId/ConversationId；在可能向 ADP 发包前保存唯一 RequestId 与 `ADP_SEND_ARMED`。重启后此状态保守判未知，不盲目重投。
- 消费真实 `request_ack`、`error`、`response.completed` 及 ReplyMethod：确认成功为 `ADP_SUCCEEDED`，能证明**业务执行前**被拦截的为 `ADP_REJECTED`，出站/执行结果不确定为 `ADP_UNKNOWN`；不能因为未看到 ACK 就推断未执行。解释真实厂商错误码，覆盖 460701、460011、460031、QPM/TPM、余额、参数、超时等；还要识别正式成功事件中的 `ReplyMethod=7` 并发超限回复，不因该值杜撰错误码或擅自推断此前未执行；不能杜撰未返回的 Code。
- **ADP 请求始终不自动重试。** 可靠协调保存结果/提示、一次待发送通知及本地占用释放；对 UNKNOWN 同样释放且通知用户先核查可能的会议副作用，后续新消息可以进入，但旧云端执行未必停止，严格会话顺序无法保证。网关不通过文字判断业务意图；会议 MCP 单独负责身份、幂等和结果查询。
- 未武装的 RECEIVED 可在重启后执行首次提交；已武装 ADP 请求、超时、断流或崩溃不能自动再次提交。保留未决消息与去重最小记录的正确清理语义。

验收：C1 100 名不同模拟用户配无额度 Fake ADP 均可获准同时转发（不等于无限物理吞吐）；C2 模拟 ADP 30 名额并发拒绝时仅对实际被拒绝者生成真实错误解释，不假定恰好 70 条失败；C3 同用户双消息竞态只提交一条；C4 限额/明确入口拒绝/模糊超时分类准确；C5 UNKNOWN 保存、释放、允许新轮次且不重投旧 RequestId；C6 armed 崩溃不重复执行；C7 不同用户会话/结果隔离；C8 CLI/原 HTTP 回归不退化。

### 阶段 D：统一回复、BUSY 与 ADP 错误通知

**依赖**：阶段 C 的可靠处理结果与待通知意图；真实企微 Secret 和出口 IP 到阶段 F 才需要。

实施：
- 统一发送 ADP 正式回答、`USER_BUSY`、明确拒绝的真实错误码/解释、`ADP_UNKNOWN` 的风险提示；不同用户的结果只发给原用户；不创建“发送失败通知的失败通知”。
- 独立通知状态 `PENDING → SEND_ARMED → SEND_ACCEPTED/SEND_FAILED/SEND_UNKNOWN`；只在企业微信应用发送接口返回 `errcode=0` 且单用户目标不在 `invaliduser/unlicenseduser` 等集合中时认定 API 已接受。**不追踪员工在线、已读或终端展示**。
- 未武装的通知可在重启后恢复首次发送；SEND_ARMED 后响应丢失则记 UNKNOWN，默认不盲目重发。仅可证明未接受、且修正原因可恢复的错误允许有限重发同一已保存提示；绝不再调用 ADP，也不占用用户会话。
- 测试发送器只能产生 `SEND_SIMULATED`；真实发送适配器用 Fake HTTP 核验 Token 缓存、payload、长文本、错误/无效接收人和未知网络结果，真实平台探测阶段 F 再做。
- 首期以文字为准；ADP 如返回无法由文字表达的重要媒体类型，须说明渠道暂不支持完整呈现，不应静默当作全部发送成功。

验收：D1 A/B 用户的正常、BUSY、限额和 UNKNOWN 通知均无串发；D2 发送失败/未知不重复调用 ADP，不导致用户忙碌；D3 HTTP 200 但 `errcode≠0`、无效接收人、Token 过期正确分类；D4 已武装发送崩溃不双发，未开始发送可恢复；D5 模拟成功不等于真实企微 API 接受。

### 阶段 E：JSONL 日志、HTTP 本地/内网与 Docker 联调（当前交付终点）

**依赖**：阶段 A～D 已完成；使用独立测试会话与消息目录、已发布 ADP 测试应用及本机 Python / Docker。**不依赖公网地址、HTTPS 证书或企业微信真实回调配置。**

实施：
- 复用 Python `logging`，为网关增加统一 JSONL Formatter，老 CLI 的文本日志保持兼容；事件字段、脱敏、轮转与未来 Cosmos 边界以 [docs/wecom-integration/02_结构化日志事件.md](02_结构化日志事件.md) 为唯一 Owner。
- 使用 `message_key` 关联入站、ADP 请求、回复保存、模拟发送和错误恢复；默认不记录员工问答正文、Token、AppKey、Secret 或加密密钥。当前不接 Azure SDK，不向 Cosmos DB 写入。
- 在 PyCharm 启动同一 FastAPI 应用，本机用 `127.0.0.1:8000`、固定测试签名 GET/POST 与 TestClient 验证；现有 `/healthz` 和 `/api/v1/chat` 仍按原有单用户 Contract 工作，新 `/wecom/callback` 仅接受企业微信协议格式的可信请求，不增加绕开验签的生产测试接口。
- Docker Compose 和现有离线发布流程在可信内网完成相同 HTTP 测试（目标宿主地址 `10.102.70.82:4560` 只有实际部署可达后才可声称已验证）；使用单进程/单 worker、独占消息目录和持久挂载，核实重启恢复、权限、退出及回滚。不直接将未鉴权的 `/api/v1/chat` 暴露公网。
- 使用受控的真实 ADP 文字两轮 Probe 校验上下文；外部测试需明确环境、费用及潜在 MCP 写操作影响，不能把 Fake SSE 测试等同于真实 ADP 平台记忆。运行原有回归、文档链接与示例检查，不新增 CI Job。
- 完成后同步 [README.md](../../README.md)、[docs/README.md](../README.md) 和必要运维文档，准确区分已实现功能、模拟验收及仍未完成的真实接入。

验收：E1 JSONL 可解析/关联/脱敏，包含 BUSY、拒绝、UNKNOWN、释放与独立发送事件；E2 本机真实 HTTP 夹具覆盖可靠 ACK、100 名模拟员工、Fake ADP 30 配额、同用户并发拒绝；E3 PyCharm/Docker 故障注入证明 RECEIVED 安全续做、已武装 ADP/发送不重放、UNKNOWN 不锁用户；E4 原有 CLI、单用户 API、配置/会话兼容；E5 有界真实 ADP 两轮上下文及错误结构测试，不能调用真实会议 MCP 执行不受控并发；E6 **只能宣称 A～E 本地/内网验收，不代表企业微信真实客户端接入成功**。

### 阶段 F：真实企业微信接入与端到端验收（后续独立任务）

**依赖**：阶段 A～E 的验证证据、实际可被企业微信云端访问且符合后台配置要求的回调 URL（HTTP/HTTPS；优先 HTTPS）、真实 CorpID/AgentId、应用 Secret、Token/EncodingAESKey、测试员工可见范围、API 可信公网出口 IP 和可用发送权限。本阶段暂缓，不阻塞阶段 A～E。

实施：
- 先确认目标自建应用是否已有其他系统占用“接收消息 API”回调及原管理员/服务 Owner，禁止直接覆盖或轮换正在使用的 URL、Token、EncodingAESKey；必要时使用独立测试应用或经批准的回调转发。
- 将企业微信实际回调配置到**已经实现的同一个** `GET/POST /wecom/callback`；HTTP 与 HTTPS 不分叉业务实现，若使用 HTTPS 则可由企业可信的 TLS 反向代理终止加密。私有 IP 和 `127.0.0.1` 不可能直接成为企业微信云端可达地址。
- 在正式应用凭证和受控出口 IP 下验证 `access_token` 与 `/cgi-bin/message/send`，真实发送 API 确认接受后才允许记录 `SEND_ACCEPTED`；验证过期/错误码、未知结果与发送失败恢复。
- 用两名真实员工逐项验收：发文字→加密回调→去重落盘→腾讯 ADP 本轮完成→企业微信主动发送；同员工连续多轮、不同员工隔离；退出应用、返回查看、设备差异与网络异常。企业微信 API 接受不等于员工已读或永久保存，须记录实测边界。
- 若未来选择不同渠道（如企业微信智能机器人 WebSocket），须单独批准变更接入协议和身份模型，不能把机器人接入冒充现有自建应用回调升级。

验收：F1 管理后台 GET 校验通过、真实加密 POST 可达；F2 至少两名员工的正常多轮、同用户 BUSY 和独立错误提示可见，UNKNOWN 后可继续；F3 真实发送的接受/明确拒绝/无效收件人/结果未知分类有证据；F4 离开应用不取消服务端任务、无需已读追踪；F5 不影响已有回调使用者并有回退方案。没有外部可达入口时报告 F `blocked/not started`，不得写成已接入。

## 3. 后续扩展（不属于第一期交付）

| 触发条件 | 扩展方向 | 关键兼容/证据 |
| --- | --- | --- |
| 消息数量、任务查询或多实例确实需要共享写入 | 文件消息存储 → 数据库 | 保留唯一消息键、状态版本、未完成任务、去重标记、原子接管；冻结旧单实例并验证迁移/回滚 |
| 公司确认 Cosmos DB 账户类型、权限、预算与查询需求 | 本地 JSONL → 批量 Cosmos DB 日志采集 | 独立上传进程、稳定事件 id+分区键、上传检查点、重复上传去重、TTL/数据保留、脱敏 |
| 需要自定义 H5 聊天记录页面 | 身份认证的消息历史/状态 REST API | 区分企微原生会话与自定义页面，避免假设企微自动同步 H5 |
| 实际收到图片/文件需求 | 企业微信 MediaId 下载 → ADP 文件输入 | 媒体权限、可用期、大小限制、临时链接安全、失败与清理 |
| ADP Agent 要创建/修改会议 | MCP 可信身份、业务授权、幂等/结果查询 | 不能信任模型填写的操作者，未知 ADP 结果不能重复创建会议 |
