## 0. 目标、限制与完成定义

用户可观察结果：企业员工在**企业微信自建应用原生消息会话**发文字，网关通过可信回调确认员工身份，保存消息并快速 ACK，后台交给 ADP 单轮 `chat()`，最后把回答主动推送给该员工。员工切出应用/重新进入不应取消服务端请求；多员工可并行、同员工有序，跨重启能区分哪些动作可恢复、哪些已进入未知结果，不让会议 MCP 被盲目重复执行。

**已经决定**：单企业单应用、可信企业微信 UserID 作为 ADP UserId/VisitorId、稳定派生 ConversationId、同员工新消息忙碌即拒绝而不排队、不同员工不设置人为 ADP 业务并发限额、ADP 零自动重试与限额错误解释、UNKNOWN 通知后释放本地占用、通知状态与 ADP 会话占用解耦、不判断追问是否完成或员工已读、单实例 JSON 快照与统一普通日志、PyCharm + Docker Compose、首期不引入数据库/Redis、未来 Cosmos DB 仅评估用于**日志**。**当前阶段 A～E 只需要本机/可信内网 HTTP 与测试协议夹具**，不要求公网域名、HTTPS 证书或真实企微应用 Secret。

**尚未完成**：阶段 F 全部真实接入验收；Cosmos DB、H5 页面仍未实现。YNND 的真实加密回调和 API 接受已有直接证据，完整交付仍以本表实际门禁为准。**不提前扩展**：多租户、群聊、附件、OAuth 前端、MCP 写操作身份传递与生产回调之外的内部公共 REST API。当前 `/api/v1/chat` 仍是无鉴权、固定身份的单用户接口，不能被当作企微回调路由，更不能暴露到公网。

工程上的协议/鉴权属于高风险边界；正式实现阶段必须按项目与当前 canonical Agent_Skills 的 Coding/Testing/Docs/Review/Git 门禁进行，不能仅因阶段拆分就降低验证要求。本文是长期 roadmap，不作为第二份自动生成 Change 文档。

## 1. 核心架构选择

| 设计选择 | 推荐结论 | 实际原因 |
| --- | --- | --- |
| 一条消息一个 JSON vs 追加 JSONL | **JSON 快照做业务状态、普通 .log 做诊断与事件** | 状态要频繁更新/按 MsgId 定位；追加事件需要回放与压缩。迁移数据库依赖状态接口，不依赖 JSONL |
| 企业微信用户退出应用 | **服务器继续处理 + 企微应用主动推送** | 不是客户端同步 SSE，员工离开时不会取消服务器任务；真正展示/历史依赖企微客户端，要实测 |
| 日志与状态是否共用存储 | **分离** | 诊断日志不能替代可恢复任务状态；Cosmos 故障不能引起 ADP 副作用重复执行 |
| 同用户连续新消息 | **忙碌即拒绝，不自动排队** | 首次接收时原子占用；相同 MsgId 先去重，不重复生成通知 |
| 跨用户并发 | **不设人为 ADP 业务配额** | 尽可能立即异步转发；ADP 决定配额拒绝，网关仅做物理资源保护 |
| ADP 结果未知 | **保存 UNKNOWN、释放本地会话并通知** | 不自动重投；接受旧云端轮次可能仍执行、上下文可能重叠 |
| 企业微信消息发送 | **独立记录 API 结果，不跟踪已读** | API 接受即完成网关发送，失败不重新调用 ADP |
| HTTP 与 HTTPS 是否两套程序 | **同一 FastAPI GET/POST 回调路径** | 本地 HTTP 可验证业务协议；以后若满足真实企微可达性要求，可原路径接入 HTTP 或经 TLS 反向代理接入 HTTPS；仅传输层不同 |

### 阶段 B：企业微信回调、原子接收决策与可靠 ACK

**依赖**：阶段 A、本机 HTTP、模拟 CorpID/AgentId、测试 Token/EncodingAESKey；不依赖公网、真实 Secret 或员工端。

实施：

### 阶段 C：异步 ADP 转发、错误分类和持久化恢复

**依赖**：阶段 B；正式状态与失败语义 Owner 为 [docs/wecom-integration/01_网关架构设计.md](01_网关架构设计.md)。

实施：
- 在现有消息快照上扩展 `update/list_unfinished/purge`、版本检查、目录独占、可靠原子替换、启动重建占用及安全恢复；不另造任务数据库/Redis。
- 新网关出站使用真正的异步 HTTPS/SSE，独立用户并发，**不加模型配额业务信号量/限额队列/自动重试**。保留必要的连接池、磁盘、内存等物理资源保护。原 `main.py`、CLI、单用户 `/api/v1/chat` 与互斥行为保持兼容。
- 每条获准消息以可信 WeCom UserID 形成独立 UserId/VisitorId/ConversationId；在可能向 ADP 发包前保存唯一 RequestId 与 `ADP_SEND_ARMED`。重启后此状态保守判未知，不盲目重投。
- 消费真实 `request_ack`、`error`、`response.completed` 及 ReplyMethod：确认成功为 `ADP_SUCCEEDED`，能证明**业务执行前**被拦截的为 `ADP_REJECTED`，出站/执行结果不确定为 `ADP_UNKNOWN`；不能因为未看到 ACK 就推断未执行。解释真实厂商错误码，覆盖 460701、460011、460031、QPM/TPM、余额、参数、超时等；还要识别正式成功事件中的 `ReplyMethod=7` 并发超限回复，不因该值杜撰错误码或擅自推断此前未执行；不能杜撰未返回的 Code。
- **ADP 请求始终不自动重试。** 可靠协调保存结果/提示、一次待发送通知及本地占用释放；对 UNKNOWN 同样释放且通知用户先核查可能的会议副作用，后续新消息可以进入，但旧云端执行未必停止，严格会话顺序无法保证。网关不通过文字判断业务意图；会议 MCP 单独负责身份、幂等和结果查询。
- 未武装的 RECEIVED 可在重启后执行首次提交；已武装 ADP 请求、超时、断流或崩溃不能自动再次提交。保留未决消息与去重最小记录的正确清理语义。

- <a id="AC13"></a> **C2** 模拟 ADP 30 名额并发拒绝时仅对实际被拒绝者生成真实错误解释，不假定恰好 70 条失败。

### 阶段 D：统一回复、BUSY 与 ADP 错误通知

**依赖**：阶段 C 的可靠处理结果与待通知意图；真实企微 Secret 和出口 IP 到阶段 F 才需要。

实施：
- 统一发送 ADP 正式回答、`USER_BUSY`、明确拒绝的真实错误码/解释、`ADP_UNKNOWN` 的风险提示；不同用户的结果只发给原用户；不创建“发送失败通知的失败通知”。
- 独立通知状态 `PENDING → SEND_ARMED → SEND_ACCEPTED/SEND_FAILED/SEND_UNKNOWN`；只在企业微信应用发送接口返回 `errcode=0` 且单用户目标不在 `invaliduser/unlicenseduser` 等集合中时认定 API 已接受。**不追踪员工在线、已读或终端展示**。
- 未武装的通知可在重启后恢复首次发送；SEND_ARMED 后响应丢失则记 UNKNOWN，默认不盲目重发。仅可证明未接受、且修正原因可恢复的错误允许有限重发同一已保存提示；绝不再调用 ADP，也不占用用户会话。
- 测试发送器只能产生 `SEND_SIMULATED`；真实发送适配器用 Fake HTTP 核验 Token 缓存、payload、长文本、错误/无效接收人和未知网络结果，真实平台探测阶段 F 再做。
- 首期以文字为准；ADP 如返回无法由文字表达的重要媒体类型，须说明渠道暂不支持完整呈现，不应静默当作全部发送成功。

验收保持D1～D5原有语义，机器锚点别名为AC20～AC24：

- <a id="AC20"></a> **D1** A/B 用户的正常、BUSY、限额和 UNKNOWN 通知均无串发。
- <a id="AC21"></a> **D2** 发送失败/未知不重复调用 ADP，不导致用户忙碌。
- <a id="AC22"></a> **D3** HTTP 200 但 `errcode≠0`、无效接收人、Token 过期正确分类。
- <a id="AC23"></a> **D4** 已武装发送崩溃不双发，未开始发送可恢复。
- <a id="AC24"></a> **D5** 模拟成功不等于真实企微 API 接受。

### 阶段 E：日志、HTTP 本地/内网与 Docker 联调（已交付；历史使用 JSONL）

**依赖**：阶段 A～D 已完成；使用独立测试会话与消息目录、已发布 ADP 测试应用及本机 Python / Docker。**不依赖公网地址、HTTPS 证书或企业微信真实回调配置。**

实施：

### 阶段 F：真实企业微信接入与端到端验收（联调进行中）

**依赖**：阶段 A～E 的验证证据、实际可被企业微信云端访问且符合后台配置要求的回调 URL（HTTP/HTTPS；优先 HTTPS）、真实 CorpID/AgentId、应用 Secret、Token/EncodingAESKey、测试员工可见范围、API 可信公网出口 IP 和可用发送权限。本阶段暂缓，不阻塞阶段 A～E。

实施：
- 先确认目标自建应用是否已有其他系统占用“接收消息 API”回调及原管理员/服务 Owner，禁止直接覆盖或轮换正在使用的 URL、Token、EncodingAESKey；必要时使用独立测试应用或经批准的回调转发。
- 企业微信对外回调地址由同一TOML的`wecom.callback_url`配置，应用启动按其路径注册同一套GET/POST处理器；省略或留空时兼容`/wecom/callback`。URL的公网主机/端口与`deployment`本机监听分开，修改后重启服务并同步后台。HTTP与HTTPS共用验签、解密及可靠状态；若使用HTTPS可由反向代理终止加密。私有IP和`127.0.0.1`不能直接成为企业微信云端可达地址。
- 在正式应用凭证和受控出口 IP 下验证 `access_token` 与 `/cgi-bin/message/send`，真实发送 API 确认接受后才允许记录 `SEND_ACCEPTED`；验证过期/错误码、未知结果与发送失败恢复。
- 用两名真实员工逐项验收：发文字→加密回调→去重落盘→腾讯 ADP 本轮完成→企业微信主动发送；同员工连续多轮、不同员工隔离；退出应用、返回查看、设备差异与网络异常。企业微信 API 接受不等于员工已读或永久保存，须记录实测边界。
- 若未来选择不同渠道（如企业微信智能机器人 WebSocket），须单独批准变更接入协议和身份模型，不能把机器人接入冒充现有自建应用回调升级。

验收：F1 管理后台 GET 校验通过、真实加密 POST 可达；F2 至少两名员工的正常多轮、同用户 BUSY 和独立错误提示可见，UNKNOWN 后可继续；F3 真实发送的接受/明确拒绝/无效收件人/结果未知分类有证据；F4 离开应用不取消服务端任务、无需已读追踪；F5 不影响已有回调使用者并有回退方案。没有外部可达入口时报告 F `blocked/not started`，不得写成已接入。
