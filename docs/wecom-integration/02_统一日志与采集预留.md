# 统一普通日志与未来 Cosmos DB 采集预留

> 当前版本只写普通文本 `.log`；不再生成独立 `events-*.jsonl`。**Cosmos DB 尚未接入**。历史阶段 E 曾使用 JSONL，旧文件不会自动删除或迁移。业务事实源仍是消息快照，不是日志。

## 为什么这样设计

开发和运维人员希望从同一份日志同时排查 ADP、企业微信回调、消息状态与发送故障。普通文本行保留时间、源码文件、行号、级别及诊断文字；关键业务状态由稳定的 `gateway_event ` 标记及后续单行 JSON 机器字段补充，方便未来采集器可靠提取，避免解析自由文本。

这是**单一日志文件流、两类记录**，不是两个文件/两套业务日志。事件与普通诊断都经过同一个 `logging` Handler；既有普通日志仍可能有单用户问答预览，必须按权限管理。

## 当前实现与边界

- [src/core/logging.py](../../src/core/logging.py)：人类可读前缀、北京时间、脱敏、按大小轮转、写失败安全告警。
- [src/core/events.py](../../src/core/events.py)：网关业务事件名、状态、UUID、关联标识与字段白名单，输出到同一普通日志；不负责文件写入、轮转或消息状态。
- [src/application/wecom_gateway.py](../../src/application/wecom_gateway.py) 与 [src/application/wecom_worker.py](../../src/application/wecom_worker.py)：产生接收、去重、忙碌、ADP 出站/结果、发送、恢复与清理事件。
- [src/storage/messages.py](../../src/storage/messages.py)：消息快照的唯一可靠事实源，日志写入失败不允许改变 ACK、状态、重试或恢复决策。
- [config.example.toml](../../config.example.toml)：`log_enabled`、`log_level`、`log_file`、`log_max_bytes`、`log_backup_count`、`log_question`、`log_answer_chars`。原 `events_retention_days` 暂保留为兼容配置，但对普通日志不再生效。

网关业务事件输出样式示意（示例值不是真实执行结果）：

```text
[2026-11-08 15:30:12.123 events.py L100] [INFO] gateway_event {"schema_version":"adp_chat.log.v1","id":"example-uuid","event":"adp.completed","status":"success","message_key":null,"attributes":{"source":"test_fixture"}}
```

真实事件还包含时间、环境、组件、请求关联和可选错误字段；机器字段的精确生成与验证以 [src/core/events.py](../../src/core/events.py) 和 [tests/test_gateway_events.py](../../tests/test_gateway_events.py) 为准。普通诊断行不带 `gateway_event ` 标记，不应被当作业务事件解析。

## 哪些日志有排障价值

| 类别 | 记录什么 | 主要价值 |
| --- | --- | --- |
| ADP | 发送前武装、开始、完成、拒绝、结果未知、请求 ID、耗时与错误码 | 区分明确拒绝与可能已执行，防止盲目重试 |
| 企业微信入站 | 认证拒绝、接收、可靠保存、去重、同用户忙碌 | 定位重复消息、无 ACK、消息遗漏 |
| 企业微信出站 | 通知武装、发送开始、模拟、API 接受、拒绝或结果未知 | 区分发送器执行、云端接受和用户已读 |
| 恢复与清理 | 重启恢复、状态释放、清理成功/失败 | 排查重启后漏处理、重复执行或资源异常 |
| 人类诊断 | 安全错误分类、源码位置、异常阶段与相关标识 | 快速定位代码故障与上下游依赖 |

`message_key` 是消息链路关联入口；`request_id` 关联 ADP 单次调用；`conversation_id` 关联多轮会话。未知字段、正文、密钥、原始厂商错误信息不能绕过白名单写入事件。模拟成功不等于真实企微接受，云端接受也不等于员工已读。

## 轮转、敏感信息与故障边界

- 单一 `.log` 按 `log_max_bytes` 轮转，保留 `log_backup_count` 份旧日志；**不再按事件日期独立分段，也不再由 `events_retention_days` 清理**。
- 写入失败只记录安全告警与进程内计数，不触发业务重试；若磁盘长期故障，诊断日志仍可能丢失。
- `log_question` 与 `log_answer_chars` 只控制原有单用户入口的正文诊断，网关事件始终不含问答正文；实际示例配置开启部分正文，生产建议显式关闭。
- 日志中的会话 ID、消息哈希和请求标识仍应按敏感业务元数据限制访问；不允许把原始 Token、AppKey、Secret、密文或未脱敏异常直接写入。
- 历史 `events-*.jsonl` 不会自动删除；需要运维依据保留策略人工核查后清理，不能在升级时静默销毁。

## 后续接入 Cosmos DB 的前置条件

目前**没有采集器、Cosmos SDK、连接凭据或上传后台任务**。未来只需在日志持久化之后增加独立进程，不让 ADP 请求等待数据库写入：

1. 读取普通日志与轮转备份，按固定 `gateway_event ` 标记解析事件机器字段；其他普通诊断行可保留原文并按独立受控 Schema 提取时间/级别/源码位置。
2. 为普通诊断行定义稳定的采集 ID；网关事件复用已有 UUID，**不能在每次重读文件时重新生成 ID**。
3. 设计轮转期间的原子读取、偏移检查点、半行隔离、断点恢复、幂等与积压监控。当前有限备份会在 Cosmos 长期不可用时覆盖未采集日志，必须先解决该数据完整性风险。
4. 明确 Cosmos DB API、查询方式、分区键、TTL、费用和敏感数据政策；严格限定哪些诊断字段允许上传。
5. 先在隔离环境验证轮转、并发、进程崩溃、重复投递、数据库拒绝及网络中断；日志故障不能影响业务状态。

这只是未来集成边界，不代表当前日志已具备可靠远程采集保证。部署与查看方法见 [docs/adp-chat/02_Docker部署与运维.md](../adp-chat/02_Docker部署与运维.md)。
