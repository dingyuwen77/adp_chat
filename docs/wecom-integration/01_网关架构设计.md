# 企业微信自建应用消息网关：架构设计（HTTP 本地联调优先，待实施）

> **状态：方案设计，尚未实现企业微信网关。** 可复用能力以本文链接的当前源码和配置为准；正式编码前重新核对目标版本。
> **交付分界：**阶段 A～E 以本机/可信内网 HTTP 完成协议模拟、真实 ADP 测试、持久化和 Docker 验证，不要求公网回调；阶段 F 才验证企业微信真实消息接入和主动回复。
> 相关：[docs/wecom-integration/03_实施路线图.md](03_实施路线图.md)（实施计划）、[docs/wecom-integration/02_结构化日志事件.md](02_结构化日志事件.md)（结构化日志契约）。

## 1. 为什么需要这个服务

目标：企业内部员工在**企业微信自建应用原生消息会话**里发文字，Python 网关负责**验签、可靠接收、转发给 ADP、发送应用消息回复**。ADP 承担自然语言、追问、上下文、Agent/MCP 等业务逻辑。网关**不判断“本题是否完成”**，每次收到员工新消息只调用一次 ADP 单轮对话。

首期硬范围：**一个企业、一个自建应用、一个 ADP 逻辑应用、员工单聊、纯文字、一个运行实例、本地文件状态持久化**。不引入数据库、Redis、独立任务队列产品、H5 自定义聊天 UI 或群聊；附件、微信客服、跨企业身份、会议 MCP 可信授权与 Cosmos DB 实际上传均属后续阶段。

**当前先做什么：**在测试进程或本机 `http://127.0.0.1:8000/wecom/callback` 使用测试密钥生成的真实协议格式 GET/POST 请求；在可信内网部署时可用 `http://10.102.70.82:4560/wecom/callback`。这两条计划路由目前尚不存在。企业微信云端不能直接访问 `127.0.0.1` 或通常不可路由的 `10.x.x.x` 私网地址；没有外部可达 URL 时，不宣称员工已经能够在企业微信中真实收发消息。

**HTTP 与 HTTPS 的边界：**两者可使用同一个 FastAPI `GET/POST /wecom/callback` 路由，协议和业务处理不分叉；HTTPS 以后可由企业认可的反向代理终止 TLS 后转发给内部 HTTP。接收回调必须实现企业微信签名校验和 AES 解密，不能因为本地使用 HTTP 就取消验签。现有未鉴权的 `POST /api/v1/chat` 只限可信内网，严禁把它随回调暴露到公网。Python → 腾讯 ADP 的出站通信仍使用官方 HTTPS SSE，不受入站 HTTP 选择影响。

**本地模拟的证据边界：**测试夹具使用专用 Token/EncodingAESKey 生成合法密文，并走正式回调处理函数；模拟 `UserID` 只是测试输入，不能证明真实企业微信员工身份。模拟发送器只能记为 `SEND_SIMULATED`，不能记成真实企业微信 API 的 `SEND_ACCEPTED`。正式 GET 校验/POST 回调以及真实发送需要阶段 F 再验证。

**为何必须先写文件、再返回 200：**ADP 可能远慢于企微回调的响应窗口；必须先完成去重、同用户接收决策和可靠落盘再快速 ACK，否则 ACK 后进程退出可能丢消息。获准的不同用户请求由后台尽可能立即异步提交 ADP，**不设置人为的 ADP 业务并发配额**；超额是否被接受由 ADP 决定。Python 仍需保护有限的磁盘、内存、连接和任务资源；保护触发时不能假装已可靠接收。

## 4. 身份与唯一会话

1. 回调 GET 验证 URL，POST 验签/解密后核实 CorpID、AgentId、消息类型与 FromUserName。Token + EncodingAESKey 负责企微回调可信性；应用 Secret 用来换取企微 access_token；ADP AppKey 只用于调用 ADP。Secret 均不得进入仓库、业务消息文件或日志。
2. 单企业内部员工场景，ADP UserId **直接取**正式企业微信回调验签解密后可信的 UserID；兼容当前 ADP V2，VisitorId=UserId。本地模拟可使用测试 UserID 验证派生与隔离，但不能冒充真实员工认证。不支持将聊天正文中自称的用户身份传给模型作为鉴权。
3. **每个员工只使用一个 ADP ConversationId**。但企微 UserID 往往短于 ADP V2 要求的 32～64 个字符，不直接原样赋值。建议 `sha256("adp_chat:wecom:v1" + 明确分隔的 CorpID、AgentId、ADP 逻辑应用名、UserID)` 的 64 个小写十六进制字符，无须维护 UserID→ConversationId 映射文件。
4. ADP 逻辑应用名是固定配置值，不能使用可轮换的 AppKey；上线后派生算法、字段顺序/分隔和命名空间不可静默改变。测试应证明同用户跨重启 ID 一致、不同用户分离。
5. ConversationId 恒定只确保网关复用同一会话标识，**不保证 ADP 永久记忆全部对话**；记忆由 ADP 应用配置与平台约束决定。
6. 后续 ADP→会议 MCP 的写操作必须另外完成可信服务身份及用户权限校验、业务幂等；不能直接信任模型生成的 UserID。

### 4.1 多用户并发与原子会话占用（待实现）

- **不同员工：**不预设 ADP 并发名额，不使用人为 `max_adp_concurrency` 限额或按模型配额等待执行的队列；获准消息尽可能立即异步提交。100 名员工同时到来、模型上限 30 时，ADP 可能直接拒绝部分请求，但不保证恰好 70 条失败，还受其他请求、应用 QPS/QPM/TPM 及请求完成速度影响。**尽可能立即提交不等于无限物理资源**。
- **同一员工：**同一 ConversationId 在本地最多有一条已获准且尚无终态的请求，刚获准尚未出站也算占用。新 MsgId 立即可靠记录 `REJECTED_USER_BUSY` 和一次通知；**不排队、不自动延后执行、不调用 ADP**。用户等待前一轮结束后需要主动重新发一条新消息。
- **原子性：**可信回调先按 (CorpID, AgentId, MsgId) 去重；新的 MsgId 在单进程临界区内完成用户占用检查、获准/拒绝决策、对应快照可靠持久化及内存索引更新。重复 MsgId 不新投 ADP、不重发提示。重启时校验快照并重建用户占用，不能用独立用户锁文件和消息文件的无事务两步提交。
- **终态和释放：**ADP 成功、确认在执行前拒绝、或结果未知时，把**处理结果、待通知意图与本地占用释放**协调可靠提交。通知随后异步发送，发送失败/未知不重新占用会话。`ADP_UNKNOWN` 本地释放后，云端旧轮次仍可能执行：因此同一 ConversationId 的严格云端顺序无法保证；涉及会议写操作需 MCP 独立幂等及结果核查。
- **资源安全：**保留连接池、内存、磁盘、文件和发送任务的实际资源保护及告警，但不能把它们假冒为 ADP 模型业务配额。无法可靠接收入站消息时不得返回成功 ACK；不要无限制创建内存任务。

## 5. 用户退出应用、再次进入会怎样？

- **员工发消息后离开应用**：回调已可靠落盘，ADP_STARTED 任务在服务器继续执行，用户退出界面不影响后台请求。
- **在回复生成之前再次打开**：还没有最终回复，因此不能“取回一个尚未生成的回答”；用户可能只看到原来的消息。网关暂不提供进度查询 API。
- **ADP 完成之后**：网关通过企微 /cgi-bin/message/send 主动向原员工发送应用消息；无需用户一直在线，也不需要员工重新发问。之后在原生应用会话中的可见性由企微客户端/消息保存设置决定。
- **不能保证的内容**：主动发送 API 返回成功只表示企微 API 接受请求，不能推出设备已同步、用户已阅读、所有设备永久可见；必须使用真实企业微信客户端测试“离开→等待→重进、跨设备”。
- **发送失败或结果未知**：保留已保存的 ADP 结果；企业微信发送器分别记录 SEND_FAILED 或 SEND_UNKNOWN，必要时告警/人工核查。仅确认**消息未被接受**且可修复的错误允许有限重发同一通知；出站后不知结果则不盲目重发。**不再调用 ADP，也不阻塞用户会话**。发送接口明确接受即为网关发送完成，不跟踪在线或已读。
- **如果将来改为自建 H5 聊天首页**：原生应用会话与 H5 页面不是同一个前端历史系统，届时才需要额外的受身份认证的历史/任务查询 REST API。本期不做。

## 6. 文件方案与 JSONL 比较

消息状态是“这条消息**现在**应做什么”，运行日志是“这条消息**曾经**发生什么”。

| 选型 | 单消息 JSON 快照（本期采用） | 追加式 JSONL 消息事件流（本期不采用） |
| --- | --- | --- |
| 单条 MsgId 查找 | 哈希文件名直接定位 | 需要扫描或额外索引 |
| 状态更新 | 写临时文件并原子替换 | 追加新事件，重启需重放恢复最新状态 |
| 文件异常 | 单条快照独立修复/隔离 | 处理不完整尾行、重放、轮转、压缩 |
| 过期删除 | 按终态删除单文件 | 分段轮转与压缩，不能直接删除中间事件 |
| 换数据库 | 以稳定状态接口迁移 | 仍需事件投影与状态迁移 |

JSONL **更适合日志**。未来数据库迁移的低成本来自稳定的 `put_if_absent/get/update/list_unfinished/purge` 操作语义、固定消息主键和版本化状态，而不是文件扩展名。

**单实例文件状态约束（待实施）：**

- 对普通文字消息，以 `(CorpID, AgentId, MsgId)` 生成稳定的文件名 `message_key`；未含 MsgId 的事件单独处理，不冒充聊天消息。
- 去重检查和首次落盘在单一写入进程内互斥；同目录临时文件、flush/fsync、原子发布后才能 ACK；重复 MsgId 不重投 ADP。
- 保存 schema_version、message_key、受信身份、接收序号、待处理正文、ConversationId、ADP RequestId、原子接收决策、ADP 处理状态、待发送通知/回复、独立发送状态及必要错误；忙碌拒绝同样是可去重的快照。JSON 快照是唯一任务事实源，JSONL 只负责诊断。
- 单进程、独占数据目录；Uvicorn 1 个 worker，但进程内部允许有界并发线程。PyCharm 与 Docker **不能同时指向同一 runtime 文件目录**。
- 同一会话在本地一次最多有一条获准的未完成请求；新消息忙碌即拒绝，不排队；不同用户尽可能并行。企微回调到达顺序未必等于用户真实发出顺序。ADP_UNKNOWN 后允许新消息，但不能承诺云端旧轮次已结束或严格有序。
- 状态恢复前先读取文件并校验结构/版本，文件损坏不可静默当作新消息重入。

### 状态与失败处理

以下状态是**拟议契约**而非现有实现。ADP 请求和企业微信通知是独立的两个状态维度：

~~~text
可信入站 → 原子判定
  ├─ 已存在 MsgId → DUPLICATE，直接 ACK，无额外任务/提示
  ├─ 同用户占用中 → REJECTED_USER_BUSY + 通知 PENDING
  └─ 空闲 → RECEIVED（占用）→ ADP_SEND_ARMED（预存 RequestId）
                                    ├─ ADP_SUCCEEDED
                                    ├─ ADP_REJECTED（已证实执行前拒绝）
                                    └─ ADP_UNKNOWN（可能已执行，结果不明）
                          → 持久化结果与通知意图 + 本地释放占用

通知发送：PENDING → SEND_ARMED → SEND_ACCEPTED / SEND_FAILED / SEND_UNKNOWN
本地模拟：PENDING → SEND_SIMULATED（只能用于独立测试目录）
~~~

- `RECEIVED` 可以安全恢复尚未开始的第一次提交；`ADP_SEND_ARMED` 必须在网络调用前可靠保存本轮 RequestId。进入此边界后超时/断流/崩溃即按结果未知处理，**不自动重投**，即使实际上还没发包也采取保守策略。为避免已成功出站却因为未保存 RequestId 而重复执行，失败则不得发送。
- `request_ack` 有助于确认请求已被接受，但**缺失 ACK 不证明 ADP 未执行**。只有厂商明示的执行前拦截/拒绝证据才记 `ADP_REJECTED` 并提示用户稍后手动重试；SSE `error`、HTTP 失败、`response.completed` 及 ReplyMethod 均需按当前阶段判断。实际 Provider Code 必须保留，不得猜测；未知副作用按 `ADP_UNKNOWN` 处理。
- 对 `ADP_SUCCEEDED / ADP_REJECTED / ADP_UNKNOWN`，需要把结果/错误提示、一次待发送通知与本地用户释放**可靠协调提交**，防止先释放后宕机导致永久无反馈。`ADP_UNKNOWN` **不持续阻塞用户**，通知其本轮结果未知、涉及会议操作须先核查。后续新消息允许进入，但旧云端请求可能仍执行，无法保证同 ConversationId 的严格顺序。
- 企业微信发送仅使用保存的结果；应用消息的 HTTP 200 不足以判定成功，还需 `errcode=0`、且目标 UserID 未出现在 `invaliduser` / `unlicenseduser` 等集合。确认接受即 `SEND_ACCEPTED`，不代表员工已读。`SEND_ARMED` 后断线/重启记 `SEND_UNKNOWN` 不盲目重复推送；明确未接收且可修复时可以有限重发**同一通知**，绝不重新调用 ADP。
- 企业微信发送成功、失败或未知均不改变 ADP 会话是否已释放；发送失败不派生“发送失败的失败通知”。消息正文的生命周期按合规与消息状态单独清理。

| 故障/重启位置 | 本期必须确保的行为 |
| --- | --- |
| 签名或企业/应用校验失败 | 直接拒绝，不信任员工身份，不调用 ADP |
| 相同 MsgId 重推 | ACK，不重复 ADP，也不重复通知 |
| 同一用户两条新消息并发到达 | 只有一条原子获准；另一条保存 USER_BUSY 与待发送提示 |
| 落盘失败或物理资源不足 | 不返回已接收成功 ACK；允许企业微信按平台规则重投 |
| RECEIVED 已落盘但尚未武装 ADP 请求 | 重启后允许执行首次提交 |
| ADP_SEND_ARMED 后断流/宕机/超时 | ADP_UNKNOWN，本地保存结果、释放会话，不自动重投旧请求 |
| ADP 明确执行前拒绝（含并发/QPM/TPM） | 记录实际错误码及解释，通知员工手动重试 |
| ADP 结果可靠保存而尚未发送通知 | 重启继续首次发送已保存通知，不再次问 ADP |
| SEND_ARMED 后无法确认响应 | SEND_UNKNOWN，不自动重发，不阻塞用户 |
| 企业微信明确拒绝 | SEND_FAILED，记录结果；仅证明未接受且可修复时有限重发通知 |

单实例仍需文件写入同步、状态版本和目录独占；跨腾讯 ADP/会议 MCP 的业务副作用无法由网关保证端到端 exactly-once。员工重新发送的新 MsgId 不等于原消息网络重推，会议系统必须有业务幂等及结果查询。

### 文件自动清理规则（推荐起始值，配置可调整）

- 正式 SEND_ACCEPTED 后建议 **7 天**清理问答正文、保留不含正文的去重记录至**首次接收后 30 天**；独立保留 ADP 与发送结果。未知状态保留必要核查信息，但不默认无限期保留敏感正文。SEND_SIMULATED 只在隔离测试目录使用，不计真实发送成功。
- `FAILED_FINAL` 保留可定位失败记录至少 30 天；敏感正文按更短保留策略清理，到期按已授权处置/归档规则删除。
- RECEIVED、ADP_SEND_ARMED、待发送通知和未核查的 ADP_UNKNOWN / SEND_UNKNOWN 不能简单按年龄删除恢复或追溯证据；UNKNOWN **不持续占用用户会话**。按数据保护政策及时脱敏正文和清理已关闭状态，对积压设置文件量、磁盘用量与最老未决告警。
- 在启动和定期间隔执行小批清理；清理前重新检查终态及记录版本，不能误删运行中的任务。需要持久卷与备份，不能靠清理掩盖磁盘写入失败。
- 7/30 天是**推荐配置默认值，不是企业微信官方重试/保存期限**。保存期最终服从企业的数据保护要求。

## 7. 运行、认证与外部准备

- 本地保留 [main.py](../../main.py) CLI、现有 `/api/v1/chat` 和 `/healthz`；拟复用同一 FastAPI 应用新增 `GET/POST /wecom/callback`，并用本机 `127.0.0.1:8000`（或可信内网服务地址）完成 HTTP 联调。PyCharm 可直接启动。阶段 A～E 的签名、加解密、去重、消息恢复与模拟发送由测试夹具完成，不要求公网 HTTP/HTTPS 回调地址，也不需要真实企微应用 Secret。
- Docker Compose 初期使用一个应用进程、一个 Uvicorn worker，独占消息状态与日志持久目录；本机或可信内网 HTTP 联调。不得让两个实例共享状态目录，也不能让旧 CLI 和新网关并发修改同一个旧单用户会话文件。企微 Token/AES Key、ADP AppKey、固定逻辑应用名、状态与日志目录及资源保护参数需隔离配置；**不增加人为 ADP 业务并发名额**。真实 Secret 与可信出口 IP 在阶段 F 启用。将来 HTTPS 使用企业认可的 TLS 反向代理，业务路由不分叉。
- 阶段 A～E 可用虚构的 CorpID/AgentId/UserID 与独立测试 Token/AES Key；仅真实 ADP Probe 需要已发布测试应用 AppKey。阶段 F 再由管理员协调真实 CorpID、AgentId、Secret、已有回调归属、Token/AES Key、测试员工可见范围、外部可达回调地址及 API 可信出口 IP。
- 应用回调为 GET URL 校验与 POST 加密 XML 消息；回复由应用 Secret 获取 access_token 后调用 **企微应用消息发送 API**。不要混用微信客服 /cgi-bin/kf/ 接口。
- 企业微信主动消息接口接受并非最终到端成功或用户已读，不额外造不存在的“读回执 API”。

## 8. 实施验收与未来切换

交给 Codex 按 [docs/wecom-integration/03_实施路线图.md](03_实施路线图.md) 分阶段实现。**阶段 A～E 的交付证据**为签名加解密测试、两名模拟用户隔离与同用户忙碌拒绝、100 名模拟用户并发/模拟 ADP 30 配额拒绝、重复 MsgId、可靠 ACK、ADP_UNKNOWN 通知后释放、未知出站不重试、文件和通知恢复、结构化日志以及 PyCharm/Docker 的 HTTP 运行。**阶段 F 的独立真实验收**才要求两名员工企业微信客户端收发、员工退出再返回、真实回调和真实主动发送。A～E 通过不代表 F 通过；F 未就绪也不阻塞 A～E 文档所定义的研发完成。

后续替换数据库时：先冻结本地消息写入、备份状态、迁移未完成消息与有效去重记录、核主键/版本/序号一致，再切唯一写入 Owner；**不允许旧文件存储与新数据库同时对同一消息竞争处理**。Cosmos DB 主要计划用于结构化日志，见 [docs/wecom-integration/02_结构化日志事件.md](02_结构化日志事件.md)。
