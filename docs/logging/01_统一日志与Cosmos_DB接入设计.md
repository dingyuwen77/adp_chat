# 统一日志与 Cosmos DB 接入设计

> **状态：阶段 A/B 普通日志格式与本地解析已实现；阶段 C/D Cosmos DB 采集与查询尚未实施。** 本文描述已实现的普通日志契约与未来接入方案。当前实际输出、配置和解析器以 [src/core/logging.py](../../src/core/logging.py)、[src/core/events.py](../../src/core/events.py)、[config.example.toml](../../config.example.toml) 及 [tests/test_logging.py](../../tests/test_logging.py) 为准。历史企业微信阶段 E 的 JSONL 验收记录保留在 [docs/wecom-integration/02_实施路线图.md](../wecom-integration/02_实施路线图.md)。

## 1. 目标、范围与明确决定

日志首先为开发、运行、故障定位和跨模块关联服务，其次才是未来 Cosmos DB 的数据来源。当前实现本地普通 `.log` 与解析接口；未来再新增独立采集器，不让数据库能力侵入 ADP/企业微信业务请求。

- **保留现有前缀**：`[北京时间 文件名 L行号] [级别]`，不额外增加 `[ADP]` / `[WECOM]` 组件标签。
- **正文保留自然中文说明**：开发者根据真实代码路径自由编写，不强制固定中文模板；要准确说明动作、结果和失败边界。
- **采用方案 B**：正文说明与结构化字段之间只增加一个可见分隔符 ` | `；后面使用规范 `key=value`，不要求每条日志具有相同的业务字段。
- **不写冗余机器 JSON**：取消行尾 `record={...}`，不再输出 `gateway_event {...}` 内嵌 JSON，也不生成独立 JSONL；**不减少**既有有价值的事件、错误、关联、耗时信息。
- **全部新格式本地日志可转换**：将来采集本项目写入配置 `log_file` 的每条完整新格式日志，包括普通诊断和业务事件；不默认覆盖 Uvicorn/操作系统/其他服务的独立输出。
- **业务状态与日志分离**：消息快照仍负责可靠接收、去重、恢复、通知与重试；日志不是状态事实源。
- **现在不接入 Cosmos DB**：不添加 Azure SDK、数据库配置、上传器、后台服务、JSONL 暂存或生产数据操作。

## 2. 目标文本格式

前缀与当前实现保持一致，**仅约定正文的中文说明和键值字段分界**：

```text
[2026-11-08 19:30:12.123 client.py L181] [INFO] ADP请求完成 | request_id=abc123 conversation_id=conv456 elapsed_ms=320 status=success
[2026-11-08 19:30:13.456 wecom_gateway.py L62] [INFO] 消息已存在，跳过重复处理 | message_key=abc789 status=duplicate
[2026-11-08 19:30:15.789 client.py L186] [ERROR] ADP请求失败，服务端返回明确错误 | request_id=abc123 error_code=460031 elapsed_ms=180000 status=failed
[2026-11-08 19:30:16.000 app.py L50] [INFO] 服务启动完成
```

以上均为**设计示意，不是仓库实测输出**；实际字段应以真实数据及业务状态为准。无有意义的业务字段时不强制打印分隔符或空键值。日志每条占**一条物理行**，中文说明和可用字段完整保留；不得把多行堆栈当作新的日志记录。

### 2.1 基础字段与可选业务字段

| 类型 | 字段 | 规则 |
| --- | --- | --- |
| 固定前缀 | 时间、文件名、行号、级别 | 每条必有，不在正文重复 |
| 人工诊断 | 中文说明 | 自由编写，准确、具体，不以固定文案表限制 |
| 请求关联 | `request_id`、`conversation_id`、`message_key` | 已有真实标识且与事件有关时输出 |
| 业务状态 | `event`、`status`、`reason`、`attempt` | 有明确语义才输出；`event` 用于需要稳定聚合的业务事件，不强制所有诊断记录都有 |
| 耗时与网络 | `elapsed_ms`、`http_status` | 统一单位/类型；实际计时完成后才输出 |
| 错误诊断 | `error_code`、`error_stage`、`error_type` | 只写已确认、已脱敏的错误事实；不臆造成功或失败 |
| 可选上下文 | 来源、恢复动作、结果是否不确定、数量统计等 | 以真实代码与查询价值决定；必要时保留已有合法字段 |

字段**名称与语义**应统一，字段**集合不要求一致**。例如启动日志没有请求 ID；正常完成日志不应凭空输出 `error_code=None`。现有 `duration_ms`、`elapsed_ms` 等命名差异应在实施前核对所有生产者和消费者，再决定统一为 `elapsed_ms`，不得因重命名丢失信息或破坏回归。不要把供应商返回的“接受”描述成用户已收到/已读，也不要把执行结果未知写成明确失败。

### 2.2 解析边界和编码规则

为避免中文自由文本中的 `request_id=...` 被误判为字段，**只有固定前缀之后、正式分隔符 ` | ` 右侧才允许按键值规则解析**；左侧全部作为 `message` 保留。未来解析器必须使用确定性语法，而不是简单按所有空格或 `|` 字符切割：

1. 前缀解析：北京时间毫秒、源码文件名、`L` 行号、级别；明确 `+08:00` 的时间解释，未来输出为带时区 ISO 8601。
2. 分隔符：中文正文与字段区以独立的 ` | ` 分隔；如果中文说明本身包含相同序列，Formatter 必须按统一转义/引用规则消除歧义，或由日志调用接口分别传入正文和字段；**不能仅依赖 `split(" | ")`**。
3. 字段：规范键名 `key=value`；键名受控、重复键拒绝或明确告警；值包含空格、`=`、引号、反斜杠、`|` 等特殊字符时采用统一可逆的引用/转义规则。当前由 Formatter 与 `parse_log_line()` 统一编码/解析，回归测试约束。
4. 类型：数字、布尔、字符串和缺失值按字段语义转换；缺失不等于空字符串或 `null`，不能凭字符串猜测所有字段类型。
5. 单行：换行、回车、Unicode 行分隔符、异常栈需安全转义，保证一条记录对应一条物理行；不可把未脱敏原始异常、HTTP 查询密钥或用户正文混入字段。
6. 兼容：旧版本曾使用 ` | record=...` 和 `gateway_event` JSON；本轮已删除冗余输出；旧文件需明确版本/迁移策略。**旧格式不可冒充新格式已可无损解析**；历史文件不自动删除。
7. 解析失败：保留原始完整行及安全的错误诊断，不能静默丢弃；上传前仍需执行隐私校验。若基础前缀不可识别，应记录解析失败而非伪造时间、级别或请求标识。

当前 Formatter 支持接收“说明 + 结构化字段”的内部记录，统一输出上述文本；不要求业务调用者自行拼接、引用和转义全部字段。对仍使用自由文本的旧调用点，逐项核对后兼容或迁移，不能为了形式化大规模删减调试信息。

## 3. 诊断信息完整性与安全边界

按真实调用链检查：服务启动/停止、企业微信验签与接收、可靠保存、去重、忙碌拒绝、ADP 请求开始/完成/拒绝/结果未知、回复保存、企业微信模拟/真实发送、发送结果未知、重启恢复、状态释放与清理。重要日志应保留已存在且有诊断价值的关联 ID、真实错误码、阶段、耗时、尝试次数、结果来源与不确定性。**格式统一是信息重组，不是删日志、减少字段或降低级别。**

- `DEBUG` 用于必要的内部细节；`INFO` 用于正常进度和状态；`WARNING` 用于拒绝、结果不确定及值得关注的恢复；`ERROR` 用于真实故障。正常业务拒绝不机械升级为 ERROR。
- 不记录 AppKey、企业微信 Secret/Token/AESKey、签名、密文、访问令牌或未脱敏异常。问答正文和预览继续受现有配置控制；生产默认策略须显式核对，不能因未来“全部上传”自动放开。
- 日志写失败不得改变 ADP 调用、企业微信 ACK、发送与重试决策；**消息状态快照写失败**仍应按业务契约阻止错误的成功 ACK。
- 当前轮转由 `log_max_bytes`、`log_backup_count` 控制；本地轮转备份有限，**不能承诺未来所有历史日志永不丢失**。
- 事件名称/中文说明与业务状态要相符：云端接受不等于员工已读，ADP UNKNOWN 不等于确定失败，模拟发送不等于真实发送成功。

## 4. 未来 Cosmos DB 接入架构

```text
FastAPI / ADP Client / WeCom Gateway / Worker
                 |
          Python logging
                 |
      可读 adp_chat.log + 轮转备份
                 |
        独立 Log Collector（未来）
          ├─ 发现日志与增量读取
          ├─ 轮转识别与完整行缓冲
          ├─ 文本解析 / 类型转换 / 脱敏
          ├─ 稳定日志 ID 与幂等
          ├─ 批量上传 / 重试 / 积压监控
          └─ 上传确认后的检查点
                 |
        Azure Cosmos DB（未来）
                 |
       按时间 / request_id / message_key /
       error_code / 级别 / 中文说明查询
```

**采集范围**：本项目配置的普通 `.log` 中所有新格式日志行，既包括普通诊断也包括网关业务事件；不是只上传 `event` 记录。基础 JSON 字段包括 `id`、`timestamp`、`level`、`source_file`、`source_line`、`message`，有值的业务字段按规则扩展。中文说明完整进入 `message`；字段缺失不妨碍存储。上传前必须确认原始诊断正文是否允许进入企业数据库。

### 4.1 可靠采集与轮转

- 采集器独立进程/服务，不在 HTTP/ADP/企微热路径调用 Cosmos DB；Cosmos 故障不影响业务。
- 只处理已换行的完整记录，按**稳定文件/日志段身份 + 已确认偏移**增量读取；轮转时文件名会改变，不能只以 `.log.1` 为身份。
- 上传成功但尚未写检查点时可能重复读取：采用至少一次投递与稳定 ID 幂等，**不能在每次读取时生成随机新 ID**。可基于稳定段身份和记录起始偏移计算 ID，具体与 Cosmos 分区键/唯一性一起验证。
- 检查点只在对应批次成功确认后推进；对部分成功、429/限流、网络中断、进程崩溃、重启、损坏行分别制定恢复/告警策略。
- **上传积压保护是接入前置条件**：当前固定数量轮转备份会覆盖未上传文件；需要保留未确认数据或可恢复的本地缓冲。不能先启用上传再声称“全部日志保证入库”。

### 4.2 Cosmos DB 数据模型与查询

未来先核实公司实际使用的 Cosmos DB API（for NoSQL / MongoDB 等）、权限与网络条件；默认可以评估单一应用日志容器，但**不预先固定分区键**。根据真实日志量、常见按请求/消息关联查询、按时间与错误码筛选、数据保留期、RU/费用和索引成本选择分区键、索引与 TTL。

- 按 `request_id` 查询一次 ADP 调用链。
- 按 `message_key` 查询企业微信消息从接收至通知的处理过程。
- 按时间/级别/错误码筛选、统计耗时及排查恢复。
- 中文 `message` 原文可保留，但复杂全文检索、聚合和告警应根据需求另评估 Azure Monitor / Log Analytics；Cosmos DB 不天然等同于完整日志检索平台。
- Cosmos 的幂等唯一性必须与所选分区键一起设计；仅靠文档 `id` 不应假设能跨分区去重。

## 7. 本轮实现说明

本地 Formatter 保持原前缀；有结构化字段时正文以 ` | ` 分隔，字段按 `key=value` 编码。网关业务事件写入中文说明和 `event`、`event_id`、`status`、关联标识及 `attr_` 前缀的白名单属性；`parse_log_line()` 返回基础字段与可选业务字段的字典，不包含数据库专用 ID。已有自由文本调用点逐项按兼容规则处理，未识别的正文不强制猜测字段。**历史旧版 `record`/JSONL 不自动转换或删除**。Cosmos DB 采集、幂等、检查点、保留策略和远程验证仍属未来阶段。
