# 服务器收发排障

部署后先确认请求能从公网到达这个服务，再从已部署的容器验证它能否和 ADP、企业微信通信。业务出故障时，先保存故障时间和原请求标识，再做复测。复测说明当时的链路状态，原请求日志用于判断故障那一笔走到了哪一步。

## 一、查外网入口

当前部署的公网地址是 `115.190.218.12:3000`。在真正的外部网络执行下方命令，例如使用手机流量。通过发布域名检查时，反向代理应把 `GET /healthz` 转发到应用并保留返回状态，避免缓存或用代理自己的成功页代替。

```bash
curl -i --connect-timeout 3 --max-time 8 http://115.190.218.12:3000/healthz
```

仓库的健康响应是 `200` 和 `{"status":"ok"}`。如果看到这个结果，外网 HTTP 请求已到达应用。服务主动返回的 `503` 也说明请求到达了应用，此时优先检查本机状态和企微存储或调度。 [src/api/routes.py](../../src/api/routes.py)

外网失败时，登录服务器，分别检查容器监听端口和宿主机发布端口。当前宿主机绑定 `0.0.0.0:3000`，因此可以在服务器上使用 `127.0.0.1:3000`。

```bash
# 容器内直接请求应用
docker exec adp_channel_api python -c "from urllib.request import urlopen; print(urlopen('http://127.0.0.1:8000/healthz', timeout=3).read().decode())"

# 在宿主机上请求发布地址
curl -i --connect-timeout 3 --max-time 8 http://127.0.0.1:3000/healthz
```

| 检查结果 | 接下来查哪里 |
| --- | --- |
| 容器内无响应 | 看容器运行状态、启动日志、配置挂载和监听端口。 |
| 容器内通过，宿主机发布地址失败 | 用 `docker port adp_channel_api 8000/tcp` 核查发布映射，再查绑定 IP 和宿主机防火墙。 |
| 宿主机通过，外网失败 | 查公网 DNS、反向代理路由、端口转发、安全组、防火墙和 TLS。 |
| 外网健康检查通过，企微仍收不到 | 用下面的企微检查验证实际回调路径，另核对企微后台配置的域名、路径及代理是否传递查询参数和 XML 请求体。 |

管理端仅开放给受信任的网络和授权人员。企微公网入口按路径转发现有验签回调。需要从外网核验健康时，可额外放行只读的 `GET /healthz`。 [docs/adp-chat/02_Docker部署与运维.md](02_Docker部署与运维.md)

## 二、准备诊断

诊断默认关闭。启用前，在所有可访问应用的入口上限制 `/api/internal/diagnostics/check`，包括公网 IP 直连的 3000 端口。健康检查或企微回调需要向公网开放时，可用代理按路径限制诊断的访问来源，并封住能绕过该规则的直连入口。直连 HTTP 端口用于管理时，用防火墙将访问来源限制在可信网段或 VPN。

在服务器使用的配置文件里，把 `[diagnostics]` 下的 `diagnostics_enabled` 设为 `true`。填好要检查的目标配置后，按项目正常方式重启应用。 [config.example.toml](../../config.example.toml)

- 检查 ADP 时，直接使用 `[adp].app_key` 对应的正式应用。将 `diagnostic_adp_user_id` 设为专门保留的测试身份，区别于 `[adp].user_id`、已配置的 `[adp].visitor_id` 以及正式企微成员的 UserId。每次检查会新建独立会话。正式应用如果接入了能修改业务数据的工具，先在 ADP 侧确认该测试身份或测试流程无法触发写入。固定测试问句本身无法限制工具权限。
- 检查企微时，启用现有网关及真实发送模式。每次在命令的 `user_id` 中指定一位应用可见范围内的成员，请该成员提前打开对应企微应用会话。

从旧版升级时，`diagnostic_token`、`diagnostic_adp_app_key` 和 `diagnostic_wecom_user_id` 可以删除。旧配置仍可加载，这些字段会被忽略。停用时将 `diagnostics_enabled` 改为 `false`。回退时使用目标镜像对应的诊断配置和调用命令。

## 三、在管理网检查 ADP 和企微

在 Bash 中按可访问的入口任选一组命令，两种入口均无需令牌。执行企微检查前，将命令中的 `wecom-test-user` 替换为企业微信通讯录里的实际成员 UserId。命令在接口结束后打印 JSON 和 `HTTP` 状态码。企微检查发出测试码后最多等待 35 秒回发，等待期间终端可能没有输出。

### 通过 HTTPS 管理域名

将示例域名替换为实际允许访问诊断路径的管理域名。

```bash
adp_admin_base='https://adp-admin.example.com'

# 检查 ADP
curl -sS -w '\nHTTP %{http_code}\n' --connect-timeout 3 --max-time 55 -H 'Content-Type: application/json' --data '{"target":"adp"}' "$adp_admin_base/api/internal/diagnostics/check"

# 检查企微
curl -sS -w '\nHTTP %{http_code}\n' --connect-timeout 3 --max-time 55 -H 'Content-Type: application/json' --data '{"target":"wecom","user_id":"wecom-test-user"}' "$adp_admin_base/api/internal/diagnostics/check"
```

### 通过 HTTP IP

从已放行的可信管理来源执行下方命令。已登录服务器时，也可将第一行地址换成 `http://127.0.0.1:3000`。

```bash
adp_admin_base='http://115.190.218.12:3000'

# 检查 ADP
curl -sS -w '\nHTTP %{http_code}\n' --connect-timeout 3 --max-time 55 -H 'Content-Type: application/json' --data '{"target":"adp"}' "$adp_admin_base/api/internal/diagnostics/check"

# 检查企微
curl -sS -w '\nHTTP %{http_code}\n' --connect-timeout 3 --max-time 55 -H 'Content-Type: application/json' --data '{"target":"wecom","user_id":"wecom-test-user"}' "$adp_admin_base/api/internal/diagnostics/check"
```

**ADP** 检查从当前部署容器连接腾讯正式 ADP 地址，使用网关的 HTTP/SSE 实现。看到 `status=passed` 和 `last_ok=adp_reply_parsed`，说明正式应用成功处理了这次测试问答，服务收到了完成事件并解析出文字。遇到具体业务请求失败，仍需用原请求日志核对该次请求的身份、输入和执行阶段。 [src/adp/async_client.py](../../src/adp/async_client.py)

**企微** 检查向本次指定的成员发送一个 `ADP-DIAG-` 开头的测试码。该成员收到后，在同一应用会话将整条消息**原样作为文字发回**。接口会等回发，管理代理应给请求至少 55 秒。`send_status` 和 `receive_status` 都为 `passed`，说明企微平台接受了发送，本服务也通过验签收到了指定成员发回的本轮测试码。只有发送为 `passed` 时，先确认回发的人、测试码和等待时间，再查入站链路。`ADP-DIAG-` 后跟 32 位小写十六进制字符的完整文本保留给诊断。即使诊断已停用，迟到或误发的测试码也不会触发业务问答。 [src/application/diagnostics.py](../../src/application/diagnostics.py) · [src/api/wecom_routes.py](../../src/api/wecom_routes.py)

`HTTP 000` 表示 curl 未收到 HTTP 响应，先看 curl 的错误提示，再用第一节的健康检查核对地址和网络。`HTTP 200` 表示已经生成报告，实际检查结果看 JSON 中的 `status`。`404` 检查接口启用情况或代理路径。`409` 表示已有一轮诊断。`422` 时核对请求体，尤其是企微检查所需的单个 `user_id`。收到 `401` 或 `403` 时，检查入口的访问规则和响应来源。

## 四、按结果定位问题

保留报告里的 `diagnostic_id`、`request_id`（如有）、最后通过的 `last_ok`、失败阶段 `failed_stage` 和实际错误分类 `reason`。可能方向见 `hint`。

| 典型结果 | 优先排查 |
| --- | --- |
| `failed_stage=configuration` | ADP 检查独立测试 UserId 是否已设置且与正式身份不同。企微检查网关和真实发送模式是否已开启。 |
| `reason=dns_error` | 在同一容器检查目标域名解析和 DNS 出站策略。 |
| `reason=connect_timeout` 或连接阶段超时 | 核对容器出网、路由、安全组、出口代理和防火墙。确认拦截原因需要网络侧的丢弃或拒绝记录。 |
| `reason=tls_error` | 查容器时间、CA 证书和出口 TLS 代理。 |
| `last_ok=adp_ack` 且 `failed_stage=adp_sse` | ADP 已确认接收。按请求标识查 ADP 后续处理、SSE 返回路径或读流超时。 |
| `failed_stage=wecom_token` | 查企微 API 出网、应用凭据、可信出口 IP。 |
| `failed_stage=wecom_send` | 根据企微错误码查账号权限和应用可见范围。若结果未知，先核对客户端是否收到了。 |
| `send_status=passed` 且 `receive_status=unverified` | 先确认测试成员发出的内容和时间，再查企微回调设置、公网入口、代理和应用验签日志。 |

正式业务出故障时，记录发生时间和运行镜像。应用日志须开启，级别通常设为 `INFO`。用原聊天响应中的 `request_id`，或企微网关日志中的 `message_key`，从配置指定的应用日志查同一笔。

```bash
grep -F 'request_id=这里替换为实际ID' /实际日志目录/adp_chat.log
grep -F 'message_key=这里替换为实际键' /实际日志目录/adp_chat.log
grep -F 'diagnostic_id=这里替换为实际ID' /实际日志目录/adp_chat.log
```

聊天查“ADP请求失败”，企微查“ADP处理结果已持久化”和“企业微信通知处理结果已保存”。日志已轮转时再查对应备份。诊断报告与业务故障日志分别对应其请求时间。一条可核验的故障说明可以写成“这笔请求已进入服务，ADP 已确认接收，随后等 SSE 完成事件超时”。结果未知时，先找上游核对原请求，再决定是否重试。 [docs/logging/01_统一日志与Cosmos_DB接入设计.md](../logging/01_统一日志与Cosmos_DB接入设计.md)

## 现场验收清单

<a id="ac1"></a>

1. 从外网访问发布地址的健康接口。遇到失败时，在容器内、服务器发布地址和实际调用方三个位置定位问题。

<a id="ac2"></a>

2. 从管理网发起 ADP 检查。看到正式 ADP 应用为本轮独立会话发回成功完成事件并由服务解析出文字，才算本次收发通过。

<a id="ac3"></a>

3. 发起企微检查时在命令里指定测试成员。让该成员将应用发出的测试码原样发回，分别核对发送和接收结果。

<a id="ac4"></a>

4. 根据最后通过的步骤、失败阶段和请求标识查看本次报告或原业务请求日志。上游响应未知时先核对结果。
