# 企业微信网关实施 Roadmap（基于当前 adp_chat，尚未开始编码）

> **这是实施路线图，不是当前已完成清单。** 方案事实 Owner：[docs/企业微信接入/01_网关架构设计.md](01_网关架构设计.md)，日志契约 Owner：[docs/企业微信接入/02_结构化日志事件.md](02_结构化日志事件.md)。基线：main @ 7acea275d90079e05e25f87b698b5e859d83cd2e（2026-11-06）。每次开工重新读取仓库最新默认分支及适用 Agent_Skills Source Mode；不能用本文件代替源码事实。

## 0. 目标、限制与完成定义

用户可观察结果：企业员工在**企业微信自建应用原生消息会话**发文字，网关通过可信回调确认员工身份，保存消息并快速 ACK，后台交给 ADP 单轮 `chat()`，最后把回答主动推送给该员工。员工切出应用/重新进入不应取消服务端请求；多员工可并行、同员工有序，跨重启能区分哪些动作可恢复、哪些已进入未知结果，不让会议 MCP 被盲目重复执行。

**已经决定**：单企业单应用、企业微信 UserID 直接给 ADP UserId/VisitorId、稳定派生 ConversationId、员工只有一个逻辑对话、不判断 ADP 是否追问完成、第一版单实例文件状态、JSONL 网关日志、PyCharm + Docker Compose 都能运行、先不使用数据库/Redis、未来可迁移 Cosmos DB **日志**。

**尚未实现**：所有企业微信相关代码、消息队列与清理、网关 JSONL、Cosmos DB、H5 页面。**不提前扩展**：多租户、群聊、附件、OAuth 前端、MCP 写操作身份传递与生产回调之外的内部公共 REST API。

工程上的协议/鉴权属于高风险边界；正式实现阶段必须按项目与当前 canonical Agent_Skills 的 Coding/Testing/Docs/Review/Git 门禁进行，不能仅因阶段拆分就降低验证要求。本文是长期 roadmap，不作为第二份自动生成 Change 文档。

## 1. 先处理三个最重要的架构选择

| 设计选择 | 推荐结论 | 实际原因 |
| --- | --- | --- |
| 一条消息一个 JSON vs 追加 JSONL | **JSON 快照做业务状态、JSONL 做日志** | 状态要频繁更新/按 MsgId 定位；追加事件需要回放与压缩。迁移数据库依赖状态接口，不依赖 JSONL |
| 企业微信用户退出应用 | **服务器继续处理 + 企微应用主动推送** | 不是客户端同步 SSE，员工离开时不会取消服务器任务；真正展示/历史依赖企微客户端，要实测 |
| 日志与状态是否共用存储 | **分离** | 诊断日志不能替代可恢复任务状态；Cosmos 故障不能引起 ADP 副作用重复执行 |

## 2. 开发阶段与验收

### 阶段 A：源码/协议基线与纯身份函数（第一批）

**依赖**：当前 main、已发布 ADP 测试应用、至少一组非生产企业微信测试应用信息（真实 Secret 不入库）。

实施：
- 保留 [main.py](../../main.py) CLI 和 [adp_chat/client.py](../../adp_chat/client.py) 的单轮行为。
- 使用已验签取得的 CorpID、AgentId、WeCom UserID 和**固定配置的 ADP 逻辑应用名**确定性计算 64 个十六进制字符的 ConversationId；UserId=VisitorId=WeCom UserID，跨进程不存 UserID→ConversationId。
- 核实当前 ADP V2 格式及上下文配置；单元测试和真实跨进程两轮测试分别证明 ID 相同及平台仍能回忆先前信息。

验收：A1 同一员工同一逻辑应用跨重启 ID 一致；A2 不同员工/应用不相同；A3 当前 CLI 与 V2 兼容回归不退化；A4 明确提示“固定 ID 不等于永久记忆”。

### 阶段 B：企业微信回调接入、协议安全与可靠 ACK

**依赖**：阶段 A，企微 CorpID、AgentId、Secret、Token、EncodingAESKey、HTTPS 可达域名/测试可见范围。

实施：
- 新增独立常驻 HTTP 服务入口（建议 FastAPI）及 `GET /wecom/callback`、`POST /wecom/callback`，使用企微规范的签名、回调 URL 校验、加密 XML 解析、ReceiveId/企业/应用校验，且阻止不安全 XML/超大输入。
- 普通文字消息提取受信身份及 MsgId；非文字消息暂明确不支持；与业务无关的事件不送 ADP。
- 将去重检查、可靠消息快照创建放在 ACK 之前。失败不伪成功；重复 MsgId 不重复持久化。
- 正文和敏感配置不得进入日志。与现有 [adp_chat/config.py](../../adp_chat/config.py) 分离企微服务运行配置，不能固定使用本地测试 user_id。

验收：B1 GET URL 验证与加密 POST 正确；B2 不合法签名/解密/企业 ID 被拒绝；B3 并发重复 MsgId 只创建一条状态；B4 写盘失败不 ACK；B5 对事件与附件按明确分支响应而不静默丢弃。

### 阶段 C：文件状态、任务恢复、并发与 ADP 调用

**依赖**：阶段 B；以 [docs/企业微信接入/01_网关架构设计.md](01_网关架构设计.md) 的状态机为唯一设计 Owner。

实施：
- 建立单实例独占数据目录、消息快照接口（`put_if_absent/get/update/list_unfinished/purge`）、原子写/发布/更新、版本校验、接收序号和安全文件名；目录放 Docker Volume 或本地调试独立路径。
- 后台从 RECEIVED 领取任务，同一员工的 ConversationId 在同一时刻最多执行一轮，不同员工在配置的 ADP 并发名额内并行。新消息在状态文件中排队，不依赖额外 Redis/数据库。
- **必须先弥补当前 client.py 的 RequestId 边界**：当前 [adp_chat/client.py](../../adp_chat/client.py) 内部生成 RequestId，外部直到异常/成功才看见。为可靠的 ADP_STARTED 状态，需以最小兼容方式让调用方在实际网络发送前获得并持久化本轮 RequestId（如可校验的预发送 callback/可选 request_id），失败则不发送；不得为了这一点复制整套 SSE。
- ADP 正式完成后先持久化 `REPLY_SAVED`（回复内容可能含敏感信息，要限制访问/保留）；处理/启动异常且结果未知时标 `ADP_UNKNOWN` 并阻塞该员工后续轮次，不盲目重放。
- 进程异常关闭时自动恢复 RECEIVED 和可安全恢复的阶段；未知结果仅记录并待裁定；同一员工保证**接收顺序**，不虚称修复企微网络自身的消息到达重排。
- 以稳定终态时间执行文件清理：建议已接受发送的正文 7 天后清理、去重标记保留至首次接收后 30 天；未决 UNKNOWN/在途绝不直接过期删除，需容量告警和人工处置记录。

验收：C1 不同员工并发且无会话串线；C2 同员工两条按可靠接收顺序执行；C3 模拟刚落盘后崩溃可自动继续；C4 模拟已发起 ADP 后崩溃**不会**自动重复调用；C5 文件损坏/磁盘满/重入/过期清理不破坏去重；C6 原有 CLI 单轮协议不变。

### 阶段 D：企业微信主动回复与“离开应用”体验

**依赖**：阶段 C，企微应用 Secret、可用发送权限及企业可信出口 IP。

实施：
- 缓存企业微信 access_token（按接口实际有效期刷新）；按原员工 ID 调用企微应用主动消息 `/cgi-bin/message/send`，转换 ADP 最终文本并执行企微文本长度与格式限制。
- 先保存 ADP reply，再进入 SEND_STARTED；企微 API 接受后保存 `SEND_ACCEPTED`。明确失败按错误码分类有界重试，结果未知标 `SEND_UNKNOWN`，不盲目重发或再次调用 ADP。
- 同一客户会话多轮追问仍只是一轮接一轮转发，无 `chat_until_complete()` / 文本猜测 / 业务完成判断。
- 验收真实员工把自建应用切后台、再次进入的表现；**native 应用聊天**不需要本服务历史查询 REST API；如果真正需要 H5 历史 UI，应新建独立需求。

验收：D1 员工 A/B 不串发；D2 退出应用后 ADP 完成仍主动推送；D3 返回会话能看见企微按自身机制保留的回复（记录实测设备/版本/限制）；D4 回答发送失败无需重跑 ADP；D5 记录 SEND_ACCEPTED 不错误宣称用户已读。

### 阶段 E：统一事件日志、脱敏、清理及 Cosmos DB 预留

**依赖**：阶段 B/C/D 的真实事件边界；精确契约仅由 [docs/企业微信接入/02_结构化日志事件.md](02_结构化日志事件.md) 维护。

实施：
- 复用 Python `logging`，网关用一个事件输出封装和 JSONL Formatter；老 CLI 默认文本日志保持兼容，避免为了网关重写 [adp_chat/logging.py](../../adp_chat/logging.py) 全部行为。
- 事件覆盖回调接受/拒绝/重复、消息入库、ADP 启停/错误、reply 保存、企微主动消息接受/失败、重启恢复/未知状态与清理。
- 所有事件使用稳定 `message_key` 关联，必要时关联 ADP RequestId、ConversationId、耗时、错误阶段/代码；**默认不写员工问题/回答全文或 Token/Secret**。JSONL 大小/日期轮转并定期清理，生产日志级别 INFO。
- 不接 Azure SDK，**不在本阶段向 Cosmos DB 写日志**；本地采样验证每行可解析 JSON、必填字段、白名单字段、跨组件关联和敏感数据遮蔽。

验收：E1 一条消息可通过 message_key 贯穿入站/ADP/企微发送；E2 每行符合 v1 格式且 JSON 可解析；E3 关闭/开启 DEBUG 均不泄露凭证/原始聊天；E4 日志异常不自动重试 ADP；E5 轮转及保留清理不误删业务状态文件。

### 阶段 F：PyCharm + Docker Compose 真实联调和交付

**依赖**：阶段 A～E 均通过适用验证，已获得企业微信域名/回调/可信 IP 与 ADP 发布配置。

实施：
- 增加可在 PyCharm 直接启动的网关入口（现有 main.py 仍可测试）、Dockerfile、Compose 服务及本地/容器差异化 Secret 和数据目录配置；**一个应用实例/一个 Uvicorn worker**，容器使用持久卷，HTTPS 可复用企业现有代理。
- 健康检查、优雅关闭、独占实例锁、重启恢复、磁盘容量观察、未知任务报警/运营处置说明、备份与回滚步骤。
- 完成两个真实员工的长期多轮对话、员工离开再返回、带并发/重复回调/断流/重启的最小端到端测试。
- 文档变更后同步 [README.md](../../README.md) 的当前真实运行说明；只能在通过真实运行与验证后才把“待实施”改为“已实现”。

验收：F1 本地与 Docker 使用同一核心代码；F2 重启未完成可恢复且不重复业务副作用；F3 两位企业员工真实聊天和多轮连续；F4 现场看到回复与错误通知，完成安全/配置/日志/存储核对；F5 按实际部署环境提供回滚与数据保护证据。

## 3. 后续扩展（不属于第一期交付）

| 触发条件 | 扩展方向 | 关键兼容/证据 |
| --- | --- | --- |
| 消息数量、任务查询或多实例确实需要共享写入 | 文件消息存储 → 数据库 | 保留唯一消息键、状态版本、未完成任务、去重标记、原子接管；冻结旧单实例并验证迁移/回滚 |
| 公司确认 Cosmos DB 账户类型、权限、预算与查询需求 | 本地 JSONL → 批量 Cosmos DB 日志采集 | 独立上传进程、稳定事件 id+分区键、上传检查点、重复上传去重、TTL/数据保留、脱敏 |
| 需要自定义 H5 聊天记录页面 | 身份认证的消息历史/状态 REST API | 区分企微原生会话与自定义页面，避免假设企微自动同步 H5 |
| 实际收到图片/文件需求 | 企业微信 MediaId 下载 → ADP 文件输入 | 媒体权限、可用期、大小限制、临时链接安全、失败与清理 |
| ADP Agent 要创建/修改会议 | MCP 可信身份、业务授权、幂等/结果查询 | 不能信任模型填写的操作者，未知 ADP 结果不能重复创建会议 |
